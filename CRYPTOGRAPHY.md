#!/usr/bin/env python3
"""
КРИПТОГРАФИЧЕСКОЕ ОБЪЯСНЕНИЕ mTLS РЕАЛИЗАЦИИ

Данный файл содержит подробное объяснение криптографических процессов,
используемых в реализации mTLS соединения между банком HITsoff и партнером.
"""

# ==============================================================================
# 1. АСИММЕТРИЧНАЯ КРИПТОГРАФИЯ (Public Key Cryptography)
# ==============================================================================

"""
Асимметричная криптография использует пару ключей:
- Приватный ключ (Private Key) - СЕКРЕТНЫЙ, используется только владельцем
- Публичный ключ (Public Key) - ОТКРЫТЫЙ, может быть распространен

Применения в mTLS:

1. АУТЕНТИФИКАЦИЯ (Authentication)
   - Клиент подписывает данные своим приватным ключом
   - Сервер проверяет подпись используя публичный ключ клиента
   - Это доказывает, что данные от владельца приватного ключа

   Математика:
   Signature = Sign(Data, PrivateKey)
   Verify = Verify(Data, Signature, PublicKey)
   
   Если публичный ключ может расшифровать подпись - значит данные от владельца приватного ключа

2. РАСПРЕДЕЛЕНИЕ КЛЮЧЕЙ (Key Distribution)
   - Серверу безопасно отправить публичный ключ по открытому каналу
   - Приватный ключ никогда не передается
   - Позволяет избежать проблемы безопасного обмена ключами

3. НЕОТКАЗУЕМОСТЬ (Non-repudiation)
   - Клиент не может отрицать, что отправил данные
   - Никто другой не мог создать подпись без приватного ключа
   - Все действия могут быть аудитированы и доказаны в суде
"""

# ==============================================================================
# 2. ЦИФРОВЫЕ СЕРТИФИКАТЫ (Digital Certificates)
# ==============================================================================

"""
Цифровой сертификат связывает публичный ключ с идентичностью:

Структура сертификата X.509:
┌─────────────────────────────────────────┐
│ TBS (To Be Signed) Certificate:         │
│  ├─ Version: V3                         │
│  ├─ Serial Number: 1234567890           │
│  ├─ Signature Algorithm: sha256WithRSAEncryption
│  ├─ Issuer: C=RU, O=HITsoff Bank, CN=HITsoff-CA
│  ├─ Subject: C=RU, O=Partner Corp, CN=partner.hitsoff.local
│  ├─ Validity:                           │
│  │  ├─ Not Before: 2026-05-06 14:27:45 GMT
│  │  └─ Not After: 2027-05-06 14:27:45 GMT
│  ├─ SubjectPublicKeyInfo:              │
│  │  ├─ Algorithm: rsaEncryption         │
│  │  └─ Public Key: (2048 bit RSA key)  │
│  └─ Extensions:                         │
│     ├─ Subject Alternative Name (SAN)  │
│     ├─ Key Usage                        │
│     └─ Extended Key Usage               │
│                                          │
├─ Signature Algorithm: sha256WithRSAEncryption
└─ Signature Value: (подпись CA)         │
                                          │
Отправитель (CA) подписывает целое содержимое сертификата.
Это называется "Certificate Signing" (подпись сертификата).
"""

# ==============================================================================
# 3. ЦЕПЬ ДОВЕРИЯ (Trust Chain)
# ==============================================================================

"""
Проверка цепи доверия - это процесс верификации подписей сертификатов:

ИЕРАРХИЯ:
┌─────────────────────────┐
│  ROOT CA (Корневой ЦА) │ ← Самоподписанный, в его мы доверяем
└────────┬────────────────┘
         │ Подписывает (Sign)
         ↓
┌─────────────────────────┐
│  Server Certificate     │ ← Подписан ROOT CA
│  (Сертификат Сервера)   │   Клиент проверяет подпись ROOT CA
└─────────────────────────┘    используя PublicKey из ROOT CA

ПРОЦЕСС ПРОВЕРКИ:
1. Клиент получает Server Certificate
2. Клиент извлекает "Issuer" из сертификата: "CN=HITsoff-CA"
3. Клиент находит ROOT CA сертификат с CN=HITsoff-CA
4. Клиент проверяет подпись Server Certificate используя PublicKey из ROOT CA:
   
   Verify(
       data=ServerCertificate.TBSCertificate,  # Все содержимое кроме подписи
       signature=ServerCertificate.Signature,   # Подпись от CA
       publicKey=RootCA.PublicKey              # Публичный ключ CA
   ) → TRUE/FALSE

5. Если проверка пройдена - сертификат подлинный, не подделан
6. Затем проверяются другие параметры:
   - Срок действия (Not Before, Not After)
   - CN/SAN совпадают с хостом
   - Ключи использования (Key Usage) корректные

В нашем случае:
╔════════════════════════════════════════════════╗
║          CLIENT PERSPECTIVE                   ║
╚════════════════════════════════════════════════╝

1. Client загружает ROOT CA Certificate (ca-cert.pem)
2. Client подключается к Server
3. Server отправляет свой Certificate (server-cert.pem)
4. Client проверяет:
   ✓ Подпись Server Certificate с помощью ROOT CA PublicKey
   ✓ Срок действия сертификата
   ✓ CN/SAN содержит 127.0.0.1 (или другой адрес)
5. Если все ОК - Client доверяет Server

╔════════════════════════════════════════════════╗
║          SERVER PERSPECTIVE                   ║
╚════════════════════════════════════════════════╝

1. Server загружает ROOT CA Certificate (ca-cert.pem)
2. Client отправляет свой Certificate (client-cert.pem)
3. Server проверяет:
   ✓ Подпись Client Certificate с помощью ROOT CA PublicKey
   ✓ Срок действия сертификата
   ✓ Другие параметры (CN, Organization, etc)
4. Если все ОК - Server доверяет Client и позволяет доступ
"""

# ==============================================================================
# 4. TLS HANDSHAKE С ВЗАИМНОЙ АУТЕНТИФИКАЦИЕЙ
# ==============================================================================

"""
TLS Handshake - это процесс установки защищенного соединения.

С mTLS (взаимной аутентификацией) процесс:

CLIENT (Партнер)                    SERVER (Банк)
    │                                    │
    │─────── 1. ClientHello ────────────→│
    │    - TLS Version 1.2+              │
    │    - Supported Cipher Suites       │
    │    - Session ID                    │
    │                                    │
    │←───── 2. ServerHello ──────────────│
    │    - TLS Version                   │
    │    - Chosen Cipher Suite           │
    │    - Session ID                    │
    │                                    │
    │←─ 3. Certificate (ServerCert) ────│
    │    - Server Certificate            │
    │    - Certificate Chain             │
    │                                    │
    │←─ 4. ServerKeyExchange ────────────│
    │    - Ephemeral ECDH public key     │
    │    - Signature over handshake msgs │
    │                                    │
    │←─ 5. CertificateRequest ───────────│
    │    - Список доверяемых CA          │
    │    - Требует Client Certificate    │
    │                                    │
    │←─ 6. ServerHelloDone ──────────────│
    │                                    │
    │─────── 7. Certificate ────────────→│
    │    - Client Certificate            │ ← Ключ! Взаимная аутентификация
    │    - Certificate Chain             │   Client доказывает идентичность
    │                                    │
    │─── 8. ClientKeyExchange ──────────→│
    │    - Ephemeral ECDH public key     │
    │    - Encrypted Pre-Master Secret   │
    │                                    │
    │─── 9. CertificateVerify ──────────→│
    │    - Signature всех handshake msgs │ ← Доказательство владения приватным ключом
    │    - Подписано ClientPrivateKey    │   Только владелец приватного ключа может создать
    │                                    │
    │─── 10. ChangeCipherSpec ──────────→│
    │    - Переключиться на шифрованный  │
    │                                    │
    │─── 11. Finished ──────────────────→│
    │    - Хешированная сумма всех msgs  │
    │    - Зашифрована Master Key        │
    │                                    │
    │←─ 12. ChangeCipherSpec ────────────│
    │    - Переключиться на шифрованный  │
    │                                    │
    │←─ 13. Finished ────────────────────│
    │    - Хешированная сумма всех msgs  │
    │    - Зашифрована Master Key        │
    │                                    │
    ←───── Защищенное соединение установлено ────→
    │    Все данные теперь зашифрованы   │
    │    между Client и Server           │
    │                                    │
    │─────── 14. HTTP Request ──────────→│ (зашифрован)
    │─────── 15. HTTP Response ─────────←│ (зашифрован)
    │                                    │

КЛЮЧЕВЫЕ МОМЕНТЫ ВЗАИМНОЙ АУТЕНТИФИКАЦИИ:

1. Server требует Certificate от Client (шаг 5: CertificateRequest)
2. Client отправляет свой Certificate (шаг 7)
3. Server проверяет:
   - Подпись Client Certificate (используя CA PublicKey)
   - Срок действия
   - Доверенность в цепи
4. Client доказывает владение приватным ключом (шаг 9: CertificateVerify)
   - Client подписывает все сообщения handshake своим приватным ключом
   - Server проверяет подпись используя Client PublicKey из сертификата
   - Если подпись верна - Client владеет приватным ключом
5. Обе стороны знают, что другая сторона - это именно то, чем она претендует быть
"""

# ==============================================================================
# 5. СИММЕТРИЧНОЕ ШИФРОВАНИЕ (Session Encryption)
# ==============================================================================

"""
После успешного TLS handshake обе стороны знают "Master Secret" - общий симметричный ключ.

Этот ключ используется для шифрования всех данных в сессии:

ALGORITHM: TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA256

Компоненты:
- ECDHE: Ephemeral Elliptic Curve Diffie-Hellman
  - Обмен ключами между Client и Server
  - Каждое соединение имеет свою пару ключей
  - Perfect Forward Secrecy (даже если приватный ключ украден, прошлые сессии безопасны)

- AES-256-GCM: Advanced Encryption Standard, 256-bit, Galois/Counter Mode
  - Блоковое шифрование
  - 256-bit ключ = 2^256 возможных комбинаций
  - GCM режим обеспечивает целостность данных (аутентификация)

- SHA256: Secure Hash Algorithm 256-bit
  - Хеширование для создания Master Secret и Key Derivation
  - Односторонняя функция (нельзя восстановить исходные данные)

ПРОЦЕСС:
1. Client и Server обмениваются ephemeral ECDH ключами
2. Обе стороны вычисляют Master Secret используя:
   - Pre-Master Secret (из ECDH)
   - Client Random
   - Server Random
   - Функция PRF (Pseudo-Random Function) с SHA256
3. Из Master Secret генерируются:
   - Encryption Key (для AES)
   - MAC Key (для целостности)
   - IV (Initialization Vector)
4. Все данные шифруются с использованием AES-256-GCM

ПРИМЕР:
Сообщение: {"amount": 1000, "recipient": "ООО Компания А"}
Зашифровано (hexadecimal): a7f3 8c9d 2e4b 5f1a 9c3d 7e2b 4a6f...
Расшифровано: Обратное зашифровано с тем же ключом
"""

# ==============================================================================
# 6. ЦЕЛОСТНОСТЬ ДАННЫХ (Data Integrity)
# ==============================================================================

"""
TLS использует Message Authentication Code (MAC) для обеспечения целостности.

HMAC-SHA256:
- Hash-based Message Authentication Code
- Использует хеш-функцию SHA256 и секретный ключ
- Даже если данные зашифрованы, MAC проверяет, что они не были изменены

ПРОЦЕСС:
1. Client вычисляет: MAC = HMAC_SHA256(Data, MAC_Key)
2. Client отправляет: Encrypted(Data) + MAC
3. Server расшифровывает: Data = Decrypt(Encrypted(Data))
4. Server вычисляет: MAC' = HMAC_SHA256(Data, MAC_Key)
5. Server проверяет: MAC == MAC'?
   - Если не равны - данные были изменены
   - Если равны - данные целостны

GCM режим (Galois/Counter Mode) включает аутентификацию в шифрование,
поэтому MAC встроен в зашифрованные данные.
"""

# ==============================================================================
# 7. КРИПТОГРАФИЧЕСКАЯ БЕЗОПАСНОСТЬ В НАШЕЙ РЕАЛИЗАЦИИ
# ==============================================================================

"""
СТОЙКОСТЬ К РАЗЛИЧНЫМ АТАКАМ:

1. Man-in-the-Middle (MITM) Attack:
   ✓ Защита: mTLS требует валидные сертификаты обеих сторон
   ✓ Атакующий не может создать сертификат подписанный CA
   ✓ Даже если имитирует сервер, клиент не поверит

2. Certificate Spoofing (Подделка сертификата):
   ✓ Защита: Сертификат подписан CA (криптографическая подпись)
   ✓ Атакующий не может подделать подпись без CA PrivateKey
   ✓ Сертификат привязан к PublicKey (нельзя подменить ключ)

3. Private Key Theft:
   ✗ Риск: Если украсть PrivateKey - атакующий может выдавать себя за владельца
   ✓ Защита: Требуется немедленное отзывление сертификата (CRL/OCSP)
   ✓ Все соединения после кражи небезопасны
   ✓ Соединения ДО кражи все еще безопасны (из-за Perfect Forward Secrecy)

4. Packet Sniffing (Перехват пакетов):
   ✓ Защита: Все данные зашифрованы AES-256-GCM
   ✓ Атакующий видит только зашифрованные данные и случайный IV
   ✓ Без ключа расшифровать нельзя

5. Replay Attack (Повторное воспроизведение):
   ✓ Защита: Каждое соединение имеет уникальный Session ID
   ✓ TLS использует последовательные номера для обнаружения повторов
   ✓ Timestamp в данных помогает обнаружить старые сообщения

6. Brute Force Attack:
   ✓ Защита: 256-bit ключ = 2^256 возможностей
   ✗ Риск: Квантовые компьютеры смогут взломать RSA
   ✓ Решение: Миграция на постквантовую криптографию (CRYSTALS-Kyber, etc)
"""

┌─────────────────────────────────────┐
│ ПРИВАТНЫЕ (ОЧЕНЬ КОНФИДЕНЦИАЛЬНЫ):  │

│   - Если украсть - все небезопасно  │
│   - НИКОГДА не распространять       │
│                                     │
│ ✗ server-key.pem                    │

│   - Приватный ключ клиента          │
│   - Хранится ТОЛЬКО у клиента       │
│   - Используется для подписи данных │
│   - НИКОГДА не отправлять серверу   │
└─────────────────────────────────────┘

ПРАВИЛА БЕЗОПАСНОСТИ:
1. Приватные ключи защитить (chmod 600 на Linux/macOS)
2. Приватные ключи хранить отдельно от публичных
3. Использовать разные ключи для разных целей
4. Регулярно ротировать ключи
5. Хранить резервные копии в безопасном месте
6. Аудировать доступ к ключам
7. Использовать Hardware Security Module (HSM) для очень важных ключей
"""

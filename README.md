## РЕШЕНИЕ: mTLS с проверкой сертификатов через CA (15 баллов) ✓

Реализовано полнофункциональное решение **взаимного TLS соединения (mTLS)** между банком HITsoff и партнером с проверкой цифровой подписи через CA.

### Архитектура решения

```
┌────────────────────────────────────────────────────────────┐
│              Банк HITsoff (Сервер)                        │
│  - Требует сертификат от клиента (партнера)              │
│  - Проверяет подпись сертификата CA                       │
│  - Процесс HTTP сервера на порту 8443 с TLS              │
│                                                             │
│  ↑↓ mTLS соединение (двустороннее шифрование)            │
│                                                             │
│              Партнер (Клиент)                             │
│  - Отправляет свой сертификат серверу                     │
│  - Проверяет сертификат сервера через CA                  │
│  - Использует приватный ключ для подтверждения идентичности
└────────────────────────────────────────────────────────────┘
```

### Инфраструктура открытых ключей (PKI)

#### 1. Корневой сертификационный центр (CA)
- **Файл**: `certs/ca-cert.pem`, `certs/ca-key.pem`
- **Роль**: Подписывает сертификаты сервера и клиента
- **Действителен**: 1 год
- **Данные**: 
  - Организация: HITsoff Bank
  - CN: HITsoff-CA
  - Самоподписанный

#### 2. Сертификат сервера (банк)
- **Файлы**: `certs/server-cert.pem`, `certs/server-key.pem`
- **Роль**: Идентифицирует банк для клиентов
- **CN**: bank.hitsoff.local
- **SAN**: DNS:bank.hitsoff.local, DNS:localhost, IP:127.0.0.1, IP:0.0.0.0
- **Подписан**: CA

#### 3. Сертификат клиента (партнер)
- **Файлы**: `certs/client-cert.pem`, `certs/client-key.pem`
- **Роль**: Идентифицирует партнера для банка
- **CN**: partner.hitsoff.local
- **Организация**: Partner Corp
- **Подписан**: CA

### Процесс mTLS handshake

```
Клиент (Партнер)                           Сервер (Банк)
    │                                            │
    │─── TLS ClientHello ──────────────────────→│
    │    (поддерживаемые алгоритмы)             │
    │                                            │
    │←─── TLS ServerHello + ServerCertificate ──│
    │     (сертификат банка, подписанный CA)    │
    │                                            │
    │─── ClientCertificate ────────────────────→│
    │    (сертификат партнера, подписанный CA)  │
    │                                            │
    │─── ClientKeyExchange ────────────────────→│
    │    (зашифрованный session key)            │
    │                                            │
    │─── CertificateVerify ────────────────────→│
    │    (подпись ключом клиента)               │
    │                                            │
    │←─── ServerFinished ──────────────────────│
    │                                            │
    │    Установлено защищенное соединение      │
```

### Как это работает

#### На клиенте (партнер):
1. **Инициирует соединение** с адресом 127.0.0.1:8443
2. **Отправляет сертификат** `client-cert.pem`, подписанный CA
3. **Отправляет приватный ключ** `client-key.pem` для подтверждения владения ключом
4. **Проверяет сертификат сервера** через CA сертификат `ca-cert.pem`
5. **Отправляет запросы** (health check, validate, transfer)

#### На сервере (банк):
1. **Слушает на порту** 8443 с mTLS включен
2. **Получает сертификат клиента** и проверяет:
   - Сертификат подписан именно CA (`ca-cert.pem`)
   - Срок действия сертификата не истек
   - Цифровая подпись корректна
3. **Извлекает информацию клиента** из сертификата:
   ```
   CN=partner.hitsoff.local
   O=Partner Corp
   C=RU
   ST=Moscow
   L=Moscow
   ```
4. **Обрабатывает запросы** с верификацией идентичности

### Информация о безопасности

#### Преимущества mTLS
1. **Двусторонняя аутентификация**: Оба участника подтверждают идентичность
2. **Шифрование**: Все данные защищены TLS
3. **Целостность**: Данные не могут быть изменены в пути
4. **Неотказуемость**: Клиент не может отрицать отправку данных (приватный ключ)
5. **Проверка подписи CA**: Сертификаты не могут быть подделаны

#### Криптографические алгоритмы
- **Обмен ключами**: ECDHE (Elliptic Curve Diffie-Hellman Ephemeral)
- **Шифрование**: AES-256-GCM
- **Целостность**: SHA-256
- **Асимметричная криптография**: RSA-2048 (для ключей сертификатов)

#### Процесс подписи сертификата CA
```
1. Банк создает приватный ключ (2048-bit RSA)
2. Банк создает Certificate Signing Request (CSR)
3. CA подписывает CSR своим приватным ключом
4. Клиент получает подписанный сертификат
5. При соединении клиент проверяет:
   - Подпись CA (используя ca-cert.pem)
   - Срок действия
   - CN и SAN совпадают
```

### API сервера банка

#### 1. GET /health
Проверка здоровья сервера (не требует mTLS)
```bash
curl --cacert certs/ca-cert.pem \
     --cert certs/client-cert.pem \
     --key certs/client-key.pem \
     https://127.0.0.1:8443/health
```
**Ответ**: `{"status": "healthy", "service": "HITsoff Bank Server"}`

#### 2. GET /api/validate
Проверка mTLS соединения и информация о клиенте
```bash
curl --cacert certs/ca-cert.pem \
     --cert certs/client-cert.pem \
     --key certs/client-key.pem \
     https://127.0.0.1:8443/api/validate
```
**Ответ**: Информация о сертификате клиента

#### 3. POST /api/transfer
Отправка платежного перевода (требует mTLS)
```bash
curl -X POST \
     --cacert certs/ca-cert.pem \
     --cert certs/client-cert.pem \
     --key certs/client-key.pem \
     -H "Content-Type: application/json" \
     -d '{"amount": 1000, "recipient": "ООО Компания А"}' \
     https://127.0.0.1:8443/api/transfer
```
**Ответ**:

### Проверка сертификатов

#### Просмотр информации о сертификате
```bash
openssl x509 -in certs/server-cert.pem -text -noout
```

#### Проверка цепочки подписей
```bash
openssl verify -CAfile certs/ca-cert.pem certs/server-cert.pem
```

#### Проверка срока действия
```bash
openssl x509 -in certs/server-cert.pem -noout -dates
```

### Дополнительные сценарии безопасности

#### 1. Что происходит при подделке сертификата?
- Клиент не сможет подключиться (ошибка проверки подписи CA)
- Сервер отклонит запрос с неправильным сертификатом

#### 2. Что происходит при краже приватного ключа?
- Атакующий может выдавать себя за легального партнера
- Все соединения с этого момента небезопасны
- **Решение**: Пересоздание сертификата и распространение нового CA сертификата

#### 3. Что происходит при истечении сертификата?
- Клиент не сможет подключиться
- Необходимо пересоздать и переподписать новые сертификаты
